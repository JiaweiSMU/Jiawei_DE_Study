> [!NOTE] Delta Load
> To load those data from the OLTP that changed since the last time we pulled the data.

| Approach                       | How it works                                                                                                                                                                        | Benefits                                                                                                                                                | Cons                                                                                                                                                                                  |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [[Log-based (Write Ahead Logs)]] Write Ahead Logs | CDC reads the WAL, which the database already writes for durability                                                                                                                 | - Most **efficient**, with minimal stress on the OLTP database when loading the data<br>- No need to figure out the changes, as the WAL already does it | - Complex to implement<br>- ==Doesn't work for the initial load==, since the logs only hold recent changes                                                                            |
| [[Watermark]]                  | - `created_at` and `updated_at` columns on the OLTP side make it easy to query the latest changes<br>- **warehouse tracks the watermark** to know which row or date to extract from | - Full load and delta load use the same approach, so nothing new needs to be invented                                                                   | - The application side must implement these columns on each table<br>- Each worker that performs `INSERT` or `UPDATE` must update these columns<br>- ==Unable to track `DELETE`==     |
| [[Trigger-based]]              | A `FOR EACH ROW` trigger on `INSERT`, `UPDATE` and `DELETE` inserts each change into a dedicated log table                                                                          | - Catches all `INSERT`, `UPDATE` and `DELETE` and writes them into a log table                                                                          | - Increases load on the OLTP database: the ==trigger runs in the same transaction==, which **lengthens the transaction and holds locks longer**<br>- The log table can get very large |
| [[Scan & Hash Table]]          | Scan the table's rows, generate a hash for each row, and compare whether the data already exists in the warehouse                                                                   | - Simple to implement                                                                                                                                   | - ==Does not scale==, as it can be computationally expensive on large tables                                                                                                          |
